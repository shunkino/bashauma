# bashauma design proposal: demotion decay, weighted priority, keyword hold

**Author:** Keaton (Lead) · **Status:** design only, no code changed · **Context:** v1.0.1, `lib/scheduler.sh` (568 lines), `lib/config.sh` (137 lines), prd.md (394 lines) — §3 the OS model, §6.2–6.4 the queue and pick-next policy, §6.8 config, §12 future directions
**Companion documents:** `.squad/decisions/inbox/keaton-decay-priority-hold-design.md` (8-line summary), `.squad/decisions/inbox/fact-checker-devils-advocate-abc.md` and `.squad/agents/fact-checker/history.md` (Devil's Advocate brief, addressed in full at the end of this document)

This is the full working document — the original design (unmodified from the session that produced it) followed by a direct response to Fact Checker's independent Devil's Advocate brief, a revised implementation order, and a recommended path for Shun.

## Unifying observation

All three requests are instances of one pattern that already exists once in the shipped code: **a noisy signal gets a piece of decaying, lineage-checked state attached to it, so the scheduler can distrust it temporarily without distrusting it forever.** §6.4's false-claim demotion is the prototype; issue #1's `demotion_seq` lineage check is the hardening that makes any such state safe across pane-ID recycling. I am deliberately reusing that exact skeleton for C's hold-exemption, and extending A's decay logic into a helper both A and C call. B is architecturally different (it's about ranking, not trust) but its scoring engine is designed so A's and C's outputs (decayed count, hold state) are just two more inputs it can weigh — nothing here is a bolt-on with its own bespoke state model.

## A. `demotion_count` decay

**Decision: time decay (option 1), applied lazily at classification time, decrementing by whole elapsed windows rather than resetting to zero.**

### Why, and why not the alternatives

- **Option 2 (success-based reset) is not actually free**, contrary to the issue's framing. I traced this in the shipped code: once a pane is `is_suppressed` or `is_demoted`, `schedule()` sets `class="P1"` directly (`lib/scheduler.sh:453`) and **never calls `confirm_p0` for it again**. The "signal already being computed" doesn't exist for exactly the panes that need decay — it only exists for panes that are still full P0 candidates. Reinstating it would require probing suppressed panes specifically, which is a new cost the issue assumed didn't exist, and re-adds the noise problem decay is supposed to fix (a suppressed pane's `blocked` text is the same noisy signal that caused the false claims). Rejected.
- **Option 3 (sliding window)** requires storing a timestamp per demotion event (unbounded per-pane list) for no behavioral gain over a single decaying integer + one timestamp. Rejected as strictly more state for the same outcome.
- **Option 4 (leave it)** is what issue #1 made worse: suppression is now durable for the pane's entire lineage-verified lifetime, sharpening "no path back" into "no path back, ever, for a long-lived pane." Rejected — the issue's own reasoning already argues against this once lineage makes suppression sticky.
- **Time decay already fits the codebase's determinism model.** Aging (§6.4 item 3) is already "a wall-clock delta compared against a stored timestamp," and prd.md's determinism clause ("given the same queue state... reproducible") is already interpreted, in the shipped scheduler, as *queue state + current wall clock*, not *queue state alone* — `waited=$((now_ms - fra))` at `lib/scheduler.sh:447` already does this. Decay is the same shape of computation, so it introduces no new determinism concept, just a second field consulted the same way.

### Mechanism

- New state map `last_demotion_at` (pane_id → ms), written by `_demote_pane_to_p1` alongside `demotion_count`.
- New config `demotion_decay_seconds` (default **900**, i.e. 15 minutes per point of decay). Rationale for the default: matches the issue's own framing ("one unlucky stretch of scrollback... hours ago") — 15 minutes is long enough that decay can't be triggered by rapid back-to-back false claims within one working session, short enough that a pane touched early in a multi-hour session gets a real path back rather than needing to survive the whole session untouched. Documented as an invented constant, same status as `aging_seconds`.
- **Derive `is_suppressed` from `demotion_count >= threshold` at classification time, every yield, instead of maintaining `p0_suppressed_pane_ids` as separately-written state.** This is a simplification enabled by decay: today the array is written once, at the moment of crossing the threshold, and is otherwise just cached membership. Once `demotion_count` can move in either direction, a separately-cached array is a second source of truth that must be kept in sync with the first on every decay tick — strictly more surface for the same bug class §6.4 already worries about (staleness). Dropping the array and computing membership from the counter removes that duplication. `p0_suppressed_pane_ids` is removed from the state schema; existing state.json files with the stale key are unaffected (jq simply ignores it, and the close-pruning block's reference to it is deleted).

### Decay pseudocode (replaces the `is_suppressed`/`is_demoted` lookups inside the `status = blocked` branch of the candidate loop)

```
# Called once per blocked candidate, AFTER _lineage_trusted/_forget_stale_pane
# (decay must not run on bookkeeping that was just proven untrustworthy —
# _forget_stale_pane already wipes last_demotion_at along with demotion_count,
# so a lineage failure makes decay moot, not double-applied).

function decay_demotion_count(state, pane_id, now_ms, decay_seconds):
    count      = state.demotion_count[pane_id] // 0
    last_at    = state.last_demotion_at[pane_id]
    if count == 0 or last_at is null:
        return state   # nothing to decay

    window_ms      = decay_seconds * 1000
    elapsed_ms     = now_ms - last_at
    windows_passed = floor(elapsed_ms / window_ms)
    if windows_passed <= 0:
        return state   # not enough time has passed for even one decrement

    decrement   = min(count, windows_passed)
    state.demotion_count[pane_id] = count - decrement
    # Advance the origin by exactly the whole windows consumed, not to
    # now_ms: preserves partial progress toward the next decrement instead
    # of restarting the clock, and keeps the function a pure, reproducible
    # function of (state, now) with no hidden "last checked at" state.
    state.last_demotion_at[pane_id] = last_at + decrement * window_ms
    return state

# In the candidate loop, status == "blocked" branch:
state = decay_demotion_count(state, pane_id, now_ms, CONFIG_DEMOTION_DECAY_SECONDS)
is_suppressed = state.demotion_count[pane_id] >= CONFIG_P0_SUPPRESS_AFTER_DEMOTIONS
is_demoted    = pane_id in state.p0_demoted_pane_ids   # unchanged, epoch-scoped
```

### State schema delta

```diff
  "p0_demoted_pane_ids": [],
- "p0_suppressed_pane_ids": [],
  "demotion_count": {},
  "demotion_seq": {},
+ "last_demotion_at": {},
```
`last_demotion_at` is pruned on pane close alongside `demotion_count`/`demotion_seq` (same close-pruning block, one more key). It is wiped by `_forget_stale_pane` for the same reason `demotion_count` is.

### Config delta
`demotion_decay_seconds: 900` — new key, `_config_to_int`-coerced (it reaches `$(( ))`), `BASHAUMA_DEMOTION_DECAY_SECONDS` env override, same pattern as every other numeric knob.

### What could go wrong
- A pane that decays back under the threshold and is then immediately re-confirmed and re-demoted will re-enter the demotion count near the threshold, not at 0 — this is intended (decay is a path back, not amnesty), but should be tested explicitly so a flapping pane can't oscillate in and out of suppression every single yield in a way that's visible/annoying. Mitigate by not changing `aging_threshold`/FIFO ordering as a side effect of decay — a decayed pane re-enters P0 exactly like any other candidate, no special fast-track.
- Removing `p0_suppressed_pane_ids` touches four call sites (Phase 2 pre-fetch skip check, candidate loop, close-pruning, `_forget_stale_pane`) — mechanical but must be done atomically in one PR, not left half-migrated.

## B. Weighted priority model

### The decision: hybrid — two hard bands, one weighted score underneath

I am **not** proposing a pure weighted score across everything, and I am **not** proposing keeping the pure lexicographic cascade. Both fail one of the two stated constraints:

- A pure score risks starvation and the P0-first guarantee becoming *tunable away entirely*, which conflicts with §9's "no starvation" success metric and the "answering a blocked agent is highest payoff" thesis of §3 — those are supposed to be invariants, not defaults a bad weight config can quietly disable.
- The pure cascade is exactly what Shun is asking to move past: it cannot let a strong affinity match outrank a weak class advantage, structurally, no matter how it's tuned, because class is compared before affinity is even looked at.

So: two **hard bands** stay fixed program logic (not configurable), and a **weighted score** governs everything else.

```
Band 1 (highest, unconditional): aged P1 candidates       — starvation guarantee, §9
Band 2 (everything else): P0 candidates and non-aged P1    — ranked by weighted score
```
Band 1 stays a hard rule because it is the one thing prd.md calls a metric rather than a preference ("no runnable pane waits longer than aging_seconds past its turn" — §9). Everything in Band 2 — including the P0-vs-P1 class distinction itself — becomes a *weighted* input rather than a *sorted* one, which is the actual mechanism that lets "a strong affinity match... outrank a weak class advantage": under default weights the class term dominates (reproducing today's behavior exactly), but a user who deliberately narrows the gap gets exactly the locality-over-class tradeoff Shun described.

### Signals, and how each is scored (bounded to [0,1] unless noted)

| Signal | Component | Source (new cost?) |
|---|---:|---|
| Priority class | `class = 1` if P0 else `0` | already computed |
| Cache affinity, continuous not discrete | `affinity ∈ {1.0 tab, 0.66 workspace, 0.33 cwd, 0 none}` | already computed (`_affinity_rank`, inverted) |
| Time-to-unblock (SJF proxy) | `cheapness`, P0 only, else `0` | **reuses the existing confirm-step `pane read` — zero extra cost** |
| Agent throughput (MLFQ) | `throughput = clamp(ema_ms / saturation_ms, 0, 1)` | new bookkeeping, no new herdr calls |
| Recency/staleness | `staleness = clamp((now − last_focused_at)/saturation_ms, 0, 1)` | new bookkeeping, no new herdr calls |

`score = W_class·class + W_affinity·affinity + W_throughput·throughput + W_cheapness·cheapness − W_staleness·staleness`, sorted descending, final tie-break unchanged (`state_change_seq`, then `pane_id` — still provably total).

**Default weights are chosen so Band 2's ordering is provably identical to today's cascade for every existing test scenario**, by construction: each tier's *maximum possible combined swing* is kept strictly smaller than *one unit* of the tier above it.

```
W_class       = 1000   # max swing of everything below must stay < 1000
W_affinity    =   50   # max affinity swing (1.0) * 50 = 50 << 1000; and > throughput/cheapness/staleness combined max (≤ 9)
W_throughput  =    5
W_cheapness   =    3
W_staleness   =    1
```
With these defaults: P0 (class=1, score ≥ 1000 + ...) always outranks non-aged P1 (class=0, score ≤ 50+5+3 = 58) exactly as today. Within the same class, affinity dominates throughput/cheapness/staleness exactly as today. Only genuine ties (same class, same affinity rank) now get resolved by throughput/cheapness/staleness *before* falling to seq/pane_id — a strict refinement, not a behavior change, of the current tie path. **Zero-config goal is met**: an untouched install reproduces v1.0.1's ordering bit-for-bit on every input the existing test suite already exercises.

### Cost-of-switch vs payoff-of-switch, made explicit

The formula above already *is* this framing, just spelled out with a subtraction instead of a separate "cost" concept: `affinity` (inverted distance) and `staleness` are the cost terms; `class`, `throughput`, `cheapness` are the payoff terms. I chose to fold cost into the same additive score rather than a separate cost/payoff ratio because a ratio reintroduces non-linear surprises (a near-zero cost divides up unpredictably) that would undermine the "user can build intuition" requirement — a sum of bounded, weighted terms is far easier to reason about and to explain (see below).

### Time-to-unblock estimate, concretely

`confirm_p0` already reads the candidate's bottom `blocked_confirm_lines` and discards the text after the boolean check. Change it to also emit a cheapness estimate from the **same** read (no second `pane read`):

```
function confirm_p0_detail(pane_id) -> (confirmed: bool, cheapness: float):
    text   = herdr pane read pane_id --source visible
    bottom = last N non-empty lines of text   # N = CONFIG_BLOCKED_CONFIRM_LINES, as today
    confirmed = bottom matches CONFIG_BLOCKED_CONFIRM_PATTERN
    if not confirmed:
        return (false, 0)
    # Heuristic proxy, not exact SJF: a short, single-line confirmation
    # ("Proceed? [y/N]") is cheaper to answer than a multi-line menu the
    # user has to read through. Bounded by construction (line_count <= N).
    cheapness = 1 - (count(bottom, nonempty_line) / CONFIG_BLOCKED_CONFIRM_LINES)
    return (true, cheapness)
```
This is deliberately labeled a rough proxy in code and docs — it approximates "reading cost" by "how much of the confirmation window is filled," which is crude but free, directionally correct, and improvable later (e.g. detecting a bulleted menu vs. a single yes/no line) without changing the scoring architecture.

### Agent throughput (MLFQ), concretely

- New state: `last_dispatch_at` (pane_id → ms), `throughput_ema_ms` (pane_id → ms).
- Written at exactly the two places that already observe these transitions — **no new event source**:
  - `schedule()`, where it already marks the departure pane fed because `departure_status == "working"` → also set `last_dispatch_at[departure] = now_ms`.
  - `record_status()`, in the existing `idle|done|blocked` case branch → if `last_dispatch_at[pane]` exists, compute `duration = now_ms - last_dispatch_at[pane]`, update `throughput_ema_ms[pane] = α·duration + (1-α)·throughput_ema_ms[pane]` (default **α = 0.3**, new config `throughput_ema_alpha`), else seed it with `duration`.
- Cold start (no EMA yet): `throughput = 0.5` (neutral), not 0 — a brand-new pane must not be penalized purely for lacking history.
- `saturation_ms` default **600000** (10 min): a pane that reliably works 10+ minutes autonomously per dispatch is treated as maximally high-yield; new config `throughput_saturation_seconds`.

### Staleness

- New state: `last_focused_at` (pane_id → ms), set in `schedule()`'s winner branch at the moment `agent focus` is invoked (optimistically, matching the codebase's existing `|| true` tolerance for that call's failure — not adding new error handling for a case v1 already accepted).
- `saturation_ms` default **3600000** (1h); new config `staleness_saturation_seconds`.
- Weighted lowest of all four (`W_staleness = 1`) *by design*: aging already owns the starvation guarantee (Band 1, hard). Staleness is offered purely as a "warm the user's cold panes back up occasionally" nudge (§12's working-set-restore spirit), not relied on for fairness — so a misconfiguration here can make the scheduler feel slightly different, never unfair.

### Config surface

Named profiles for the common cases, plus a raw escape hatch for power users — mirrors the existing `blocked_confirm_pattern` vs `blocked_confirm_lines` split (structured default, regex override).

```jsonc
{
  "priority_profile": "classic",     // "classic" | "locality" | "throughput" | "custom"
  "priority_weights": {              // only read when priority_profile == "custom"
    "class": 1000, "affinity": 50, "throughput": 5, "cheapness": 3, "staleness": 1
  },
  "throughput_ema_alpha": 0.3,
  "throughput_saturation_seconds": 600,
  "staleness_saturation_seconds": 3600,
  "affinity": "tab"                  // unchanged meaning: which affinity components exist at all
}
```
- `classic` (default) → the weights above, reproducing v1.0.1.
- `locality` → lowers `class` relative to `affinity` (e.g. `class: 40, affinity: 50`) so a strong same-tab P1 candidate *can* outrank a distant P0 — this is the literal implementation of Shun's example, opt-in, never the default.
- `throughput` → raises `throughput`'s weight so high-yield agents get fed preferentially when several P1 candidates are hungry.
- Named profiles are just shipped `priority_weights` presets — no separate code path, so adding a fourth profile later is a data change, not a logic change.

### Determinism vs. predictability — the `explain` affordance

Reproducibility is preserved: score is a pure function of `(state.json, agents_json, now_ms, config)`, same as today's cascade already is (it also depends on wall-clock `now` via aging). What changes is a human's ability to predict it by eye when several weighted terms interact. Per the task's own framing, that gap is answered with inspectability, not by avoiding the feature:

- `schedule()` writes a `last_decision` object to state (or a sibling `explain.json`) on every run: the full scored candidate list, each component's raw and weighted value, and the winner — pure local write, no extra herdr call.
- A new **`explain` action** (manifest `[[actions]]` entry, same shape as `next`) invokes a read-only script that pretty-prints the last decision: *"w5:p2 won: class 1000 (P0), affinity 0 (no match), throughput 3.1 (ema 620ms), cheapness 2.4 — total 1005.5, beat w3:p1's 1002.0 by affinity."* This directly answers "how does the user inspect or explain a decision" without adding any new scheduling behavior.

### What could go wrong
- The EMA/staleness maps grow the state file by two more per-pane entries each — bounded by the same close-pruning block (extend it to prune `last_dispatch_at`, `throughput_ema_ms`, `last_focused_at`).
- A `custom` profile with a badly-chosen `class` weight (e.g. 0) *can* defeat the P0-first guarantee within Band 2 — that's the whole point of exposing it, but it means the README must say plainly that Band 1 (aging) is the only hard guarantee once `custom` is used, and that `locality`/`custom` users are trading the "P0 always wins" property away deliberately.
- This is the largest, riskiest piece — needs a battery of regression tests proving byte-identical ordering to the current cascade under `classic` across every state shape the existing 16 tests already construct, before any weight becomes user-tunable.

## C. Keyword-based transition hold

### Which pane, when, at what cost

**The departure pane's own recent output — the pane the user is currently sitting in, at the dispatch yield only.** Concretely: when `on_status_changed.sh` calls `schedule(departure_pane_id)`, before the candidate loop even runs, read `pane read --source visible` on `departure_pane_id` (the same one, not any candidate) and check its bottom `hold_check_lines` non-empty lines for a hold keyword. This is **one extra `pane read` per dispatch yield**, not per candidate — bounded exactly like the existing confirmation cost, just on a different pane.

### Only the dispatch yield — never the explicit yield

`next.sh`'s explicit yield is the user actively saying "take me somewhere else, now." Suppressing that on the strength of a keyword heuristic would fight the user's direct instruction — the single worst failure mode this feature could have. **The hold check is not even performed for the `next` path**; `schedule()` takes an explicit `is_dispatch_yield` boolean and skips the whole hold block when false. This also makes `next` the escape hatch (see below) for free, by construction, not as an added safeguard.

### Does a held pane count as fed? What happens to the queue?

Yes. The dispatch already happened — the agent legitimately has a new task — so **all normal epoch bookkeeping proceeds unchanged**: departure pane is marked fed, the previous winner's false-claim check still runs, aging clocks still tick for everyone else. **Only the final `agent focus` call is skipped**, and `last_winner_pane_id`/`last_winner_was_p0`/`winner_fired_epoch` are **not updated**, because no move happened — there is no "winner" to falsify-check next time. The rest of the queue is untouched and re-evaluated in full at the next real yield (the next dispatch, or the user pressing `next`). This is a pure no-op on top of the existing schedule, not a new state machine.

### Escape hatch — the feature cannot wedge the user

`next` always works, unconditionally, as established above. That is the entire escape hatch, and it needs no additional mechanism — the user is never trapped because the one action explicitly meaning "move me" is never subject to the hold.

### §5 / §9 compatibility — argued, not assumed

A hold produces **no `agent focus` call at all** — the null action. §9's invariant is about *unrequested* moves; a hold is the plugin declining to make a move it would otherwise have made on its own initiative, which is strictly more conservative than v1's baseline, not less. It cannot, by construction, cause an unrequested context switch, because it causes no context switch. The subtler question — does suppressing the *pick-next* step at a legitimate yield override "what the user's yield implied"? — I'd argue no: the dispatch event itself doesn't say "and also go elsewhere"; that's `schedule()`'s own policy inference, and a hold is a refinement of that policy (a documented exception), not an override of a user action, in the same way false-claim demotion is a refinement of P0 classification, not an override of herdr's `blocked` report. Compatible with §5/§9, and worth adding one sentence to §9 saying so explicitly, since a future reader shouldn't have to re-derive this.

### Default word list

**Empty by default.** The task's own framing is right: a wrong default that traps a user in a pane when they expected the normal whisk-away is a worse regression than shipping nothing, and it directly contradicts §4's zero-config goal in spirit (zero-config should mean "safe defaults," not merely "some defaults"). Ship the feature inert, but put the exact example list Shun described directly in the README/config comments as a one-line opt-in:
```json
"hold_keywords": ["run the following command", "open your browser", "paste this into your terminal", "navigate to"]
```

### Matching mechanics

- `hold_keywords`: JSON array, matched **case-insensitive, fixed-string substring** (`grep -Fqi`), not regex — a "bag of words" config aimed at non-power-users should not require ERE literacy, and fixed-string matching sidesteps both the option-injection class of bug Rai already flagged once (`confirm_p0`'s `-e` fix) and the "word contains a regex metachar and silently stops matching" failure mode.
- `hold_pattern`: optional single ERE override for power users who want real regex, same relationship `blocked_confirm_pattern` has to the simpler `blocked_confirm_lines` mechanism — mirrors existing precedent instead of inventing a new one.
- `hold_check_lines`: bottom-anchored window, default **15** (vs. `blocked_confirm_lines`'s 5) — a guide/instruction reply is prose, not a one-line prompt hint, so it needs a taller window; still bottom-anchored for the same reason §6.2 is (avoid matching stale scrollback).

### False-hold self-correction

Reuses A's exact decay pattern and issue #1's exact lineage pattern, deliberately:

```
state.hold_count[pane_id]        # incremented every time a hold fires for this pane
state.last_hold_at[pane_id]      # for decay, same helper as A
state.hold_seq[pane_id]          # state_change_seq at hold time, same lineage check as demotion_seq

At dispatch-yield entry, for the departure pane only:
    if hold_seq recorded and NOT lineage_trusted(state, departure_pane_id, observed_seq):
        forget hold_count/last_hold_at/hold_seq for departure_pane_id   # extend _forget_stale_pane
    state = decay(state, "hold_count", "last_hold_at", departure_pane_id, now_ms, CONFIG_NOISY_SIGNAL_DECAY_SECONDS)

    if departure_bottom_text matches hold_keywords/hold_pattern:
        if state.hold_count[departure_pane_id] >= CONFIG_HOLD_SUPPRESS_AFTER:
            proceed with normal scheduling   # this pane is hold-exempt for now
        else:
            state.hold_count[departure_pane_id] += 1
            state.last_hold_at[departure_pane_id] = now_ms
            state.hold_seq[departure_pane_id] = observed_seq
            do normal epoch bookkeeping, skip candidate pick + agent focus
            return
```
`CONFIG_HOLD_SUPPRESS_AFTER` default **3**, same number and same justification as `p0_suppress_after_demotions`: three repeats of a heuristic firing on the same pane without contrary evidence is the threshold the codebase already uses to decide "this is noise, not signal." `decay()` is the generalized version of A's `decay_demotion_count`, parameterized over which count/timestamp map it operates on — **one function, two call sites**, which is the concrete form of "coherent as one model" this proposal keeps promising.

**Revised below, in the response to Fact Checker's brief** — the above 3-strike raw-count design is superseded by a sharper signal (see "Response to the Devil's Advocate brief," item 3).

### State schema delta
```diff
  "last_demotion_at": {},
+ "hold_count": {},
+ "last_hold_at": {},
+ "hold_seq": {},
```
All three pruned on close, all three wiped by (the now-generalized) `_forget_stale_pane`.

### What could go wrong
- Fixed-string matching means a keyword like `"npm run"` will also fire on stale scrollback mentioning `npm run` in an unrelated context within the 15-line window — same class of false positive §6.2 already lives with for `blocked`, mitigated the same way (bottom-anchoring + self-correcting decay/exemption), not a new risk category.
- If a user sets an overly broad keyword (e.g. `"run"`), holds will fire constantly and hit the exemption threshold quickly — the exemption then does its job, but the user experience during those first three exemptions is "the scheduler didn't move me," which needs the `explain` action from B (or a minimal standalone version if B ships later) so the user can see *why* and correct their config, not just observe an inconsistency.

# Response to the Devil's Advocate brief

Fact Checker reviewed the same three items independently and reached conditions that conflict with parts of the design above. I address each objection directly, concede where he is right, and hold ground only where I still think it's warranted — with reasoning, not because I authored the original.

## 1. "prd.md §6.4 conflates reproducibility with predictability" — the crux of B

**He is right, and I concede this is the load-bearing objection.** Reproducibility (same inputs → same output, verifiable by replay) and predictability (a human can anticipate the output without running the algorithm) are different properties. §6.4's sentence — *"given the same queue state, the choice must be reproducible, so the user can build intuition about where they will land"* — states the first as if it entails the second. It doesn't. A 5-term weighted sum with floating coefficients is trivially reproducible and can still be unpredictable, because a lexicographic cascade is predictable specifically *because* it is lexicographic: each tier is a hard gate, and a human only ever needs to check tiers in order until the first one that isn't tied. A weighted score inverts that — every signal influences every decision, all the time, by an amount invisible from the terminal.

**Does the weighted model survive if predictability, not just reproducibility, is the actual requirement?** It depends entirely on which profile is active, and I think this distinction is the honest answer rather than a single yes/no:

- **Under `classic` (default) weights, as I specified them** — with the explicit constraint that each tier's maximum combined swing is strictly smaller than one unit of the tier above — the scoring function is not merely reproducible, it is **behaviorally identical to today's cascade in every case**, not just on average. That is a stronger property than reproducibility; it is isomorphism to the system that is already predictable. Under `classic`, nothing is lost, because nothing actually changed from the user's vantage point.
- **Under any tuned profile (`locality`, `throughput`, `custom`)** — the moment weights are brought close enough together that affinity can outrank class (which is the entire point of offering them), predictability is genuinely, unavoidably eroded. This is not a flaw to patch; it is the mechanism doing exactly what it was asked to do. But it means a tuned profile trades away the "build intuition" property on purpose, and that trade needs to be visible to the user making it, not hidden behind "still technically reproducible."

**Does `explain` rescue this?** No, and I want to be direct about that rather than let it read as a rescue. `explain` is a post-hoc diagnostic — it answers "why did it do that" *after* the fact. Predictability is a pre-hoc property — "what will it do next" *before* the fact, from memory alone. A system a human cannot predict does not become predictable because it can be explained afterward; explainability is a consolation prize for having already lost predictability, exactly as the brief frames it. I should not have implied otherwise in the original design.

**Where this leaves B:** I concede to Fact Checker's narrower recommendation as the actual next step. Ship Shun's literal stated example (prefer the same-workspace agent when nothing is blocked) as **one additional lexicographic tier**, not as raw weights with profiles — this satisfies the concrete ask with *zero* predictability cost, because it stays a hard gate:

```
Existing cascade: aged_rank, class_rank, affinity_rank, seq, pane_id
Revised cascade:  aged_rank, class_rank, affinity_rank, workspace_locality_rank, seq, pane_id
```
where `workspace_locality_rank` only has any effect when the runnable set is all-P1 (nothing blocked) — it is 0 if the candidate shares `workspace_id` with the currently-focused pane, 1 otherwise. This is a 5th gate, fully lexicographic, fully predictable, and directly answers the stated example without touching the architecture at all.

The full weighted/profile model (throughput EMA, cheapness/SJF proxy, staleness, named profiles) is **not abandoned as an idea**, but it is **shelved pending evidence and a prd.md amendment**, not shipped now. See "Recommended path" below for the exact gate.

## 2. Weighted model vs. an added lexicographic tier — what capability is actually lost

**I defend the narrower design; I do not defend shipping raw weights + profiles as the v1.1 deliverable.** Concretely, what's lost by staying lexicographic for now: the ability to let a *P0* candidate lose to a *P1* candidate on locality grounds (a genuinely blocked-but-far-away agent losing to a hungry-but-adjacent one) — because a new tier can only ever act *within* a class, never *across* the class boundary the way a score can. Shun's stated example ("nothing is blocked, favor the same workspace") never crosses that boundary — it's a same-class comparison, which the tier handles completely. The cross-class tradeoff (locality beating class) is a real, distinct, larger ask that nobody has asked for yet outside my own extrapolation of "mine the OS analogy hard." I should not have bundled that extrapolation into the same deliverable as the concrete example. Conceded.

## 3. C substitutes plugin judgment for expressed intent; no visibility for a false hold

**Partially conceded, with a concrete fix, not just an acknowledgment.** Two separate points here, taken separately:

**3a. Is C the same failure family as preemption?** I said in the original design that a hold "produces no `agent focus` call, so it cannot violate §9." That's still true as a mechanical claim, but Fact Checker is right that it doesn't fully answer his sharper framing: §6.1 defines dispatch itself as `sched_yield()` — the user's own act of saying "I'm done here." A hold is the plugin deciding, after that yield, that the user didn't really mean what the yield structurally means. That is a real tension, and I agree it deserves a §9 amendment scoping the invariant's language to "moves," explicitly distinguishing a move from a suppressed move — **as a clarification, not a weakening**. The behavioral guarantee itself (no `agent focus` call without a yield) is untouched and remains absolute; what changes is that the document should say plainly that a hold is a recognized, bounded exception to the *policy* that normally follows a yield, not an exception to the *invariant* itself. I hold this distinction: amend the wording, don't loosen the guarantee.

**3b. The silent-failure/visibility gap — conceded, and the original design under-specified this.** My original hold-count/decay mechanism addressed *self-correction over repeats* but not *visibility of a single event*, and not the sharper question of what signal should count as "this hold was wrong." Two concrete fixes, both cheap and consistent with existing precedent:

- **Mandatory logging of every hold event, not just repeats.** Every time a hold fires — the first time, not just the third — log it to stderr (`bashauma: held on <pane_id>, matched "<keyword>"`), exactly the channel already established for config-warning visibility (`herdr plugin log list --plugin bashauma`, decisions.md 2026-08-19T21:36:10). This cannot be a proactive notification (§5 forbids that surface outright), so "loud" in the sense a false P0 is loud is structurally unavailable to C — the best available visibility, given that constraint, is discoverability after the fact. That asymmetry is real and should be stated in prd.md as an accepted limitation, not solved away.
- **Replace the raw 3-strike counter with a sharper, user-action-triggered signal.** A false P0 is detected by a specific *contradicting user action* (leaving the pane without dispatching) — not by "the same signal firing three times." C's self-correction should use the equivalent: if the user presses `next` on the held pane within `hold_quick_next_seconds` (new config, default **30**) of a hold firing, that is direct evidence the hold guessed wrong — the user's very next action contradicts it. Treat this as a `false_hold_count` increment, separate from raw `hold_count`, and exempt the pane after a **lower** threshold — default **1**, i.e. the very first time a hold is immediately followed by an explicit override on that pane, stop holding it — since, unlike raw hold-firing (which could all be correct), a quick-`next`-after-hold is real, specific evidence of a wrong call, not just repetition. This is a meaningfully better analog to false-claim demotion than what I originally proposed, and I'm adopting it as the design going forward.

**One clarification, not a concession:** "self-expiring hold," read as "the plugin eventually moves you on its own after some time passes," is not something bashauma can do — a timer that later triggers `agent focus` is *literally* the preemption §5 rules out ("no timers that move focus"). What "self-expiring" can mean here, and does mean in this design, is that a hold's effect is scoped to exactly one yield and creates no standing veto state — the very next dispatch or `next` press is evaluated completely fresh. That was implicit in the original design but not stated clearly enough; it's stated explicitly now.

Revised state schema for C (supersedes the earlier draft):
```diff
  "hold_count": {},        # raw fires, kept for diagnostics/logging only — no longer gates exemption
  "last_hold_at": {},
  "hold_seq": {},
+ "false_hold_count": {},  # incremented only when a hold is followed by a quick `next` on the same pane
+ "last_false_hold_at": {} # same decay mechanism, applied to false_hold_count instead of hold_count
```
`CONFIG_HOLD_SUPPRESS_AFTER` now gates on `false_hold_count`, default lowered to **1**. `hold_count`/`last_hold_at` remain purely for the mandatory log line and future tuning, not for exemption logic.

## 4. Is issue #3 premature?

**Yes — fully conceded, no hedge.** I verified Fact Checker's timeline claim directly: `747db7e` (the lineage/suppression fix issue #3 is about) landed 2026-08-19 22:14:48; the Devil's Advocate brief was requested roughly 15 minutes later. The mechanism has had no wall-clock time to produce a real trigger, and issue #3 itself was speculative by construction (decisions.md logs it as "orthogonal," not as an observed-bug report). Designing decay parameters (900s, threshold interactions) against zero real data means every constant in section A above is a guess dressed as a default.

**Revised recommendation for A: do not implement decay now.** Ship a near-zero-effort, non-behavioral instrumentation step instead — log every time a pane's `demotion_count` crosses `p0_suppress_after_demotions` (entry into suppression) and every time a suppressed pane is close-pruned, to the same stderr/`plugin log list` channel, with pane_id and timestamp. No config surface, no state schema change, no prd.md change (it's a diagnostic, not a behavior). Wait for real data — if no pane accumulates a suppression that outlives a meaningful stretch of real usage, decay is solving a hypothetical and stays unbuilt; if one does, the log gives real numbers to size `demotion_decay_seconds` against instead of the invented 900s above.

## 5. Complexity budget

**Conceded as a fair critique of the original bundling; addressed by the revised order below, not by argument.** Fact Checker's point stands on its own facts: v0.1's one prior heuristic-beyond-the-core-model had to be ripped out wholesale (§11), the current scheduler is hours old, and two of the three motivating scenarios (B, C) are single hypotheticals rather than observed pain.
